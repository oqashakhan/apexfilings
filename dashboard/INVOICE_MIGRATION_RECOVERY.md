# Production invoice migration recovery — PostgreSQL / Prisma 6.19.3

Production target: **apex_filings**. No production command in this document has been executed by Codex. Stop the dashboard restart loop before running the recovery; do not delete the app, database or document volumes.

## Exact cause

Prisma applies migration directory names lexicographically. The existing names put `20261108_invoice_adjustment_rows` **before** `20261108_invoice_pricing_and_attempts`. The latter, not `20261107_professional_invoices`, creates `InvoiceLineItem` and `PaymentAttempt`. The former tries to insert into the missing line-item table. Its explicit `BEGIN` transaction aborts, and the failed history entry blocks subsequent deploys with P3009. An initial Prisma error can show only `current transaction is aborted`; inspect PostgreSQL logs for the original missing-relation error.

The previous local test applied the prerequisite before the adjustment file was introduced, hiding the clean-install ordering defect. The new regression test starts with an entirely new database and reproduces the actual failure before testing recovery.

No existing migration was renamed, edited, deleted or replaced. Merely adding a later CREATE TABLE migration cannot bypass P3009 or fix this dependency. Recovery executes the prerequisite operations first, verifies them, records that legitimately completed prerequisite with Prisma, then marks the failed adjustment attempt **rolled back** and lets Prisma execute its original INSERTs. There are no direct UPDATE/DELETE commands against `_prisma_migrations`.

## Repair files and exact table definition

The complete executable SQL is [scripts/sql/repair-invoice-prerequisites.sql](scripts/sql/repair-invoice-prerequisites.sql). It uses a transaction, a recovery advisory lock, bounded lock/statement timeouts, database-name checks and idempotent object creation. It does not update invoice totals, snapshots, orders, customers, payments, refunds or document rows. It never approves pricing or changes secrets.

`InvoiceLineItem` has TEXT primary key `id`; required TEXT `invoiceId`, INTEGER `position`, TEXT `description`; required INTEGER `quantity DEFAULT 1 CHECK(quantity>0)`; nullable INTEGER `unitCents` and `amountCents`; required TEXT `kind DEFAULT 'CHARGE'`; required BOOLEAN `approved DEFAULT false`. The unique B-tree index is `InvoiceLineItem_invoiceId_position_key(invoiceId,position)`. Its validated foreign key references `Invoice(id)` with `ON DELETE RESTRICT`. CUIDs are generated by Prisma, so there is no invented database-side ID default. Negative adjustment cents and null pending prices are legitimate.

The prerequisite also requires `PaymentAttempt`, its primary/unique/composite indexes, positive-amount check, Order foreign key, frozen snapshot-item copy, and the enabled BEFORE UPDATE/DELETE immutability trigger/function. Creating only `InvoiceLineItem` is insufficient grounds to mark the prerequisite migration applied. The repair covers all its operations. Existing rows must match the frozen snapshot at the same invoice/position; conflicting or malformed data aborts the transaction rather than being overwritten or skipped.

`verify-invoice-prerequisites.sql` asserts column types/nullability/defaults, PK/unique/composite indexes, validated parent FKs, checks, trigger binding, complete snapshot copying and correctness/uniqueness of any existing adjustment rows before replay. `verify-invoice-adjustments.sql` asserts exactly one correctly signed/value-matched row for every nonzero historical discount/tax. `audit-database-schema.mjs` checks every generated Prisma model's scalar tables/columns/types. Prisma `migrate diff` additionally verifies defaults, indexes, enums and FK behavior; it does not fully inspect custom checks/functions/triggers, so use the SQL gates too.

A new forward-only migration, `20261109_invoice_dependency_integrity`, aligns five older FKs with Prisma's `ON UPDATE CASCADE`: InvoiceLineItem→Invoice, PaymentAttempt→Order, both InvoiceCreditNote relations, and ClientReferenceHistory→User. It validates the existing parent/column/delete semantics before changing each FK. Original rows and `ON DELETE RESTRICT` remain intact. The migration also preserves each FK's deferrability, especially the deferred ClientReferenceHistory FK required by its BEFORE INSERT reference-allocation trigger. Local full-schema comparison found these five differences; production may have other drift and must be inspected rather than assumed identical.

## Coolify recovery — exact host/helper commands

These commands run in **Bash on the VPS**, not in the restarting app terminal. The recovery ZIP contains `prisma/`, `scripts/`, and this runbook. Transfer it to the VPS and extract its contents into `/root/apex-invoice-recovery` first. It contains no `.env` or secret values. The supplied Windows-side ZIP path is reported in the chat. Do not use `prisma migrate reset`, `db push`, `migrate dev`, or a production seed.

1. In Coolify, stop the **dashboard app only**, temporarily disable its automatic deployment trigger, and pause its existing email scheduled job during this maintenance window. Keep PostgreSQL and the private-document volume running. Confirm a usable backup before changing schema.
2. Open the VPS terminal. Select the stopped dashboard and running PostgreSQL container from the actual inventory. Container identifiers are deliberately requested, not guessed:

```bash
set -euo pipefail
docker ps -a --format 'table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Image}}'
read -r -p 'Dashboard container ID/name: ' APP_CONTAINER
read -r -p 'PostgreSQL container ID/name: ' DB_CONTAINER
RECOVERY=/root/apex-invoice-recovery
test -f "$RECOVERY/prisma/schema.prisma"
test -f "$RECOVERY/scripts/sql/repair-invoice-prerequisites.sql"
IMAGE=$(docker inspect --format '{{.Image}}' "$APP_CONTAINER")
APP_DIR=$(docker inspect --format '{{.Config.WorkingDir}}' "$APP_CONTAINER")
test -n "$APP_DIR"
docker inspect --format '{{range $name, $value := .NetworkSettings.Networks}}{{println $name}}{{end}}' "$DB_CONTAINER"
read -r -p 'Existing network shared by dashboard and PostgreSQL: ' DB_NETWORK
```

Use the existing app image, existing network and existing DATABASE_URL. Do not publish a database port or invent a replacement URL. Save only DATABASE_URL to a private helper environment file; the command below does not print its value:

```bash
umask 077
ENV_FILE=$(mktemp /root/apex-recovery-env.XXXXXX)
trap 'rm -f "$ENV_FILE"' EXIT
docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' "$APP_CONTAINER" |
  sed -n '/^DATABASE_URL=/p' > "$ENV_FILE"
test "$(wc -l < "$ENV_FILE")" -eq 1
chmod 600 "$ENV_FILE"
prisma_recovery() {
  docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
    --workdir "$APP_DIR" -v "$RECOVERY:/recovery:ro" --entrypoint node "$IMAGE" \
    node_modules/prisma/build/index.js "$@" --schema /recovery/prisma/schema.prisma
}
MIGRATION_ROLE=$(docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
  --workdir "$APP_DIR" --entrypoint node "$IMAGE" -e '
  const {PrismaClient}=require("@prisma/client");const db=new PrismaClient();
  (async()=>{const [r]=await db.$queryRawUnsafe("SELECT current_database() AS db,current_schema() AS schema,current_user AS role");if(r.db!=="apex_filings"||r.schema!=="public")throw new Error("Wrong database/schema");process.stdout.write(r.role);})().catch(()=>{console.error("Cannot verify production database/schema/role");process.exitCode=1;}).finally(()=>db.$disconnect());')
test -n "$MIGRATION_ROLE"
dbsql() {
  { printf '%s\n' 'SET ROLE :"recovery_role";'; cat "$1"; } |
    docker exec -i --env "RECOVERY_ROLE=$MIGRATION_ROLE" "$DB_CONTAINER" sh -c \
    'PGPASSWORD="${POSTGRES_PASSWORD:-}" psql -X -U "${POSTGRES_USER:-postgres}" -d apex_filings -v ON_ERROR_STOP=1 -v "recovery_role=$RECOVERY_ROLE"'
}
docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
  --workdir "$APP_DIR" --entrypoint sh "$IMAGE" \
  -c 'test -f node_modules/prisma/build/index.js && node node_modules/prisma/build/index.js --version'
```

The helper verifies the application connection targets `apex_filings/public`. SQL runs under that same migration role using a quoted psql identifier, so new tables do not accidentally become owned by an unrelated administrator with no app grants. The database-container administrator must be allowed to SET ROLE to the existing migration role; if not, use the existing authorized migration-role connection through your secure database access process. No new grants or credentials are created.

If the runtime image lacks the installed Prisma CLI, stop here: use the matching build image containing the project's locked dependencies. Do not install a different/latest Prisma version to recover this database. The helper must have network access to the existing DATABASE_URL hostname.

3. Back up and inspect. PostgreSQL tools here execute inside the existing database container. The backup file stays on the VPS with private permissions. Keep inspection output private because migration logs may contain operational details.

```bash
BACKUP="/root/apex_filings-before-invoice-recovery-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker exec "$DB_CONTAINER" sh -c \
  'PGPASSWORD="${POSTGRES_PASSWORD:-}" pg_dump -U "${POSTGRES_USER:-postgres}" -d apex_filings -Fc' > "$BACKUP"
test -s "$BACKUP"
docker exec -i "$DB_CONTAINER" pg_restore --list < "$BACKUP" > "$BACKUP.contents"
dbsql "$RECOVERY/scripts/sql/inspect-invoice-recovery.sql" > "$RECOVERY/before-inspection.txt"
cat "$RECOVERY/before-inspection.txt"
```

Before any repair or history resolution, also run the full-model scalar audit. Exit 1 is expected for the known missing dependency tables; review its JSON findings. Any other missing table/column/type (especially ClientReferenceHistory and the InvoiceCreditNote parents used by the forward migration) must be investigated first:

```bash
docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
  --env PRISMA_AUDIT_SCHEMA=/recovery/prisma/schema.prisma \
  --workdir "$APP_DIR" -v "$RECOVERY:/recovery:ro" --entrypoint sh "$IMAGE" \
  -c 'cp /recovery/scripts/audit-database-schema.mjs ./apex-recovery-audit.mjs && node ./apex-recovery-audit.mjs' \
  || { echo 'Review the audit findings before continuing; only the known missing dependency tables are expected.'; }
```

Confirm the database name, Invoice columns, current failed/finished migration rows, and the state of **both** InvoiceLineItem and PaymentAttempt. Check that `20261107_professional_invoices` is finished and not rolled back. Inspect `20261108_invoice_pricing_and_attempts` explicitly: it may be pending, failed or already finished. If any earlier migration is unresolved, or observed schema differs from the supplied incident, investigate it before continuing. Do not assume a migration-status label proves the physical schema is present.

4. Apply the additive prerequisite repair, then its assertion gate. Both commands must exit successfully:

```bash
dbsql "$RECOVERY/scripts/sql/repair-invoice-prerequisites.sql"
dbsql "$RECOVERY/scripts/sql/verify-invoice-prerequisites.sql"
```

If the repair command fails, its transaction rolls back. If the separate verification command fails after repair committed, the newly added objects can remain; leave migration history unresolved and investigate. Never assume verification failure undoes a previously committed repair. A lock timeout means maintenance traffic is still touching these objects; stop/review that traffic and retry rather than disabling checks. A snapshot conflict requires record review; never overwrite issued items to make verification pass.

5. Only after the complete prerequisite gate passes, record its completion **if it is pending or failed**:

```bash
prisma_recovery migrate resolve --applied 20261108_invoice_pricing_and_attempts
```

If that migration was already legitimately marked finished, skip this command; retain its original history entry and checksum. The repair fixed drift, not an unexecuted migration. `--applied` here applies only to the now fully verified prerequisite; it is never used to skip the failed historical adjustments.

6. Resolve the failed adjustment attempt as rolled back, then rerun deploy:

```bash
prisma_recovery migrate resolve --rolled-back 20261108_invoice_adjustment_rows
prisma_recovery migrate deploy
```

`resolve --rolled-back` is a metadata operation, not a physical rollback. In the confirmed incident, the explicit PostgreSQL transaction failed before its missing-table INSERT could finish, so its data changes rolled back when the connection closed. If manual recovery already inserted some adjustments, retain them: the unchanged original migration uses `NOT EXISTS` per invoice/kind and its replay is verified below. Never mark the adjustment migration applied merely to clear P3009. Once successful, rerunning `resolve --rolled-back` on the now-finished migration is incorrect; normal future runs use `migrate deploy` only.

7. Verify adjustment completeness, all prerequisite objects, and migration status:

```bash
dbsql "$RECOVERY/scripts/sql/verify-invoice-prerequisites.sql"
dbsql "$RECOVERY/scripts/sql/verify-invoice-adjustments.sql"
prisma_recovery migrate status
dbsql "$RECOVERY/scripts/sql/inspect-invoice-recovery.sql" > "$RECOVERY/after-inspection.txt"
```

Then audit the whole Prisma schema from the helper. Copying this read-only audit into the helper's workdir allows Node to resolve the image's installed dependencies; the helper filesystem is discarded afterward:

```bash
docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
  --env PRISMA_AUDIT_SCHEMA=/recovery/prisma/schema.prisma \
  --workdir "$APP_DIR" -v "$RECOVERY:/recovery:ro" --entrypoint sh "$IMAGE" \
  -c 'cp /recovery/scripts/audit-database-schema.mjs ./apex-recovery-audit.mjs && node ./apex-recovery-audit.mjs'
docker run --rm --network "$DB_NETWORK" --env-file "$ENV_FILE" \
  --workdir "$APP_DIR" -v "$RECOVERY:/recovery:ro" --entrypoint node "$IMAGE" \
  node_modules/prisma/build/index.js migrate diff \
  --from-schema-datasource /recovery/prisma/schema.prisma \
  --to-schema-datamodel /recovery/prisma/schema.prisma --exit-code
```

The scalar audit must report no missing tables/columns/types; `migrate diff --exit-code` must exit **0** for no drift (**2** means drift, **1** means error). Never pipe generated diff SQL straight into production. Inspect any additional production differences before resuming. The supplied forward FK migration produces zero drift against the current model in the local recovery test, but production may differ. The SQL assertion gates also check constraints/triggers beyond Prisma's diff coverage.

8. With all checks passed, publish the reviewed forward migration to the normal repository/deployment revision so its history remains available to future deploys. Resume the existing dashboard with one deliberate Coolify start/deployment and check `https://app.apexfilings.com/api/v1/health`, login, invoice list/detail/PDF and order/payment history. Re-enable the existing email job once; do not create a second worker. Keep the backup and private inspection output; remove the temporary helper env file (the shell trap handles it on exit). No deployment was started by this task.

The recovery bundle includes the complete migration directory so the helper can see unchanged historical files plus the new forward migration. Fresh databases have the same historical ordering dependency: run the tested prerequisite-first recovery/bootstrap sequence rather than renaming or editing migrations already used by other environments.

## Local evidence and changed files

`npm run test:migration-recovery` creates an isolated `apex_invoice_recovery_*` database, runs the full history from empty until the actual failure, confirms P3009 on retry and absence of both tables, inserts fictional business fixtures, executes the repair twice, checks prerequisite assertions, uses the exact Prisma resolve sequence, redeploys, verifies every historical adjustment, replays the original adjustment SQL, and checks no duplicates. It checks unchanged original business records, successful post-recovery user/reference creation with the deferred FK intact, immutability, unchanged historical migration-file hashes, successful migrate status, a full-model audit and a zero-drift Prisma comparison. Test databases are retained; no existing database is dropped or reset.

Changed files: this runbook; four SQL files under `scripts/sql/`; `scripts/audit-database-schema.mjs`; the **new** `20261109_invoice_dependency_integrity/migration.sql`; `tests/invoice-migration-recovery.test.cjs`; and the package.json recovery-test script. No existing migration or application feature was changed.

Recovery test, typecheck and production build passed locally. Production restoration and production-only drift checks remain operator steps because no production connection was available in this session.
